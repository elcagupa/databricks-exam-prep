Platform architecture — control plane vs data plane

Databricks splits into two planes. The control plane (Databricks-managed) hosts the UI, REST API, job scheduler, cluster manager, and Unity Catalog metastore. The data plane (customer cloud) is where compute runs — driver, workers, DBFS, and data sources. Customer data never leaves the data plane.

ComponentPlane
Web UI / REST APIControl
Job schedulerControl
Cluster managerControl
Unity Catalog metastoreControl
Driver nodeData
Worker nodes / executorsData
DBFS root storageData
JDBC / external data sourcesData
  • Driver node — orchestrates tasks; hosts SparkContext; runs driver program
  • Worker / executors — execute tasks; hold partition data in memory
  • Secure cluster connectivity — outbound-only; no open inbound ports needed
  • Serverless — Databricks manages compute in their cloud account; data plane boundary shifts
  • Delta Lake — ACID on object storage; time travel; schema enforcement; batch + streaming on same table
  • Unity Catalog — unified governance for all data, analytics, and AI assets across workspaces
Exam trap: The web application = control plane. The driver node = data plane. This is the single most common distractor in Section 1 questions.

Delta Lake core features

  • ACID transactions — serialisable isolation; concurrent reads/writes safe
  • Time travel — query any past version by version number or timestamp
  • Schema enforcement — rejects writes that don't match table schema (default on)
  • Schema evolution — opt-in via mergeSchema; adds new columns safely
  • Change Data Feed (CDF) — row-level change tracking; powers CDC pipelines
  • Unified batch + streaming — same Delta table works for both without conversion
  • Open format — Parquet files + Delta log; readable by Spark, Trino, Athena

Databricks Lakehouse platform value

  • Combines data lake (scale, openness) + data warehouse (ACID, performance) in one platform
  • Single platform for SQL, Python, Scala, R, ML, and streaming
  • Lakeflow family: Lakeflow Connect (ingest) → Lakeflow Spark Declarative Pipelines (transform) → Lakeflow Jobs (orchestrate)
  • Declarative Automation Bundles (DABs) — formerly Databricks Asset Bundles — for CI/CD
  • Partner Connect — integrate BI/ETL tools (Tableau, dbt, Fivetran, Power BI)
Exam trap: "Real-time notebook collaboration" = workspace feature. "Unified batch and streaming" = Delta Lake feature. Don't mix these categories.

Auto Loader — complete syntax high frequency

Auto Loader is the primary tool for continuously ingesting new files from cloud storage into UC-governed Delta tables. It uses the cloudFiles format and guarantees exactly-once processing via checkpointing. Two detection modes: directory listing (default — polls folder) and file notification (event-driven via cloud pub/sub — scales to millions of files).

# Auto Loader — streaming ingest to UC table df = (spark.readStream .format("cloudFiles") # required .option("cloudFiles.format", "json") .option("cloudFiles.schemaLocation", "/chk/schema") # schema enforcement / evolution .option("mergeSchema", "true") .option("cloudFiles.schemaEvolutionMode", "addNewColumns") .option("rescuedDataColumn", "_rescued") # file notification mode (high volume) .option("cloudFiles.useNotifications", "true") # throttle per micro-batch .option("cloudFiles.maxFilesPerTrigger", 1000) .option("cloudFiles.maxBytesPerTrigger", "10g") .load("/landing/events/") ) (df.writeStream .option("checkpointLocation", "/chk/events") .trigger(availableNow=True) # batch-like; preferred .outputMode("append") .option("mergeSchema", "true") .table("catalog.bronze.events") # UC-governed table )
OptionNotes
cloudFiles.formatjson, csv, parquet, avro, orc, text, binaryFile
cloudFiles.schemaLocationRequired for inference; persists schema across restarts
mergeSchematrue = add new cols; false = strict (default)
cloudFiles.schemaEvolutionModeaddNewColumns | rescue | failOnNewColumns | none
cloudFiles.useNotificationstrue = event-driven (SNS/SQS, Event Grid); false = polling

Exam trap: Without schemaLocation, schema is re-inferred from the first file on every restart — breaks on schema drift. Always set it when using schema inference.
Batch modes (exam language): "Directory listing" = polls the cloud folder. "File notification" = cloud event (SNS/SQS on AWS, Event Grid on Azure). File notification is more scalable for millions of files but requires cloud setup.

Lakeflow Connect — managed ingestion exam focus

Lakeflow Connect provides managed connector-based ingestion. It removes the need to write custom ingestion code for common enterprise sources, handles schema mapping, incremental loads, and error recovery, and writes directly to UC-governed Delta tables.

  • Standard connectors — pre-built connectors for major SaaS sources (Salesforce, ServiceNow, Google Analytics, Workday, etc.)
  • Managed connectors — partner-maintained; broader catalog of enterprise sources
  • Configured and monitored via Databricks UI or API
  • All data lands in UC-governed Delta tables — no manual schema management
  • Handles incremental loads automatically — tracks watermarks or change tokens
  • Orchestrated and scheduled via Lakeflow Jobs
  • Replaces custom JDBC + scheduling code for many common source types
Choose Lakeflow Connect when…
Source is a well-known SaaS app (Salesforce, ServiceNow)
You need governance out of the box without custom code
Ingestion frequency is daily/hourly — not sub-minute
Semi-structured/JSON data from enterprise APIs
You need reliable incremental loads with error handling managed for you
Choose JDBC/REST in notebook when…
Source is a relational database with custom SQL needed
You need full control over query logic and transformation
Lakeflow Connect doesn't support the source
Schedule via Lakeflow Jobs on top

JDBC / REST ingestion in notebooks

# JDBC: read from relational DB into DataFrame jdbc_url = "jdbc:postgresql://host:5432/mydb" df = (spark.read .format("jdbc") .option("url", jdbc_url) .option("dbtable", "public.orders") .option("user", dbutils.secrets.get("scope","user")) .option("password", dbutils.secrets.get("scope","pw")) .option("numPartitions", 8) .option("partitionColumn", "order_id") .option("lowerBound", 1) .option("upperBound", 1000000) .load() ) # Write to UC-governed Delta table df.write.mode("overwrite").saveAsTable("catalog.bronze.orders")
# REST API ingestion import requests token = dbutils.secrets.get("scope", "api-token") resp = requests.get( "https://api.example.com/v1/records", headers={"Authorization": f"Bearer {token}"}, params={"page": 1, "limit": 500} ) data = resp.json()["results"] # Convert to Spark DataFrame and write to UC df = spark.createDataFrame(data) df.write.mode("append").saveAsTable("catalog.bronze.api_records")
JDBC parallelism: Use numPartitions + partitionColumn + lowerBound/upperBound for parallel reads. Without these, Spark reads the entire table with one connection — very slow for large tables.

Bronze → Silver cleaning pattern high frequency

The Silver layer transforms raw Bronze data: clean nulls, standardise types, deduplicate, and write to a new UC-governed table. This is the most commonly tested ETL pattern.

# Read bronze, clean, write silver from pyspark.sql.functions import ( col, to_date, to_timestamp, trim, upper, lower, when, coalesce, lit, regexp_replace, count, count_distinct, avg, sum, mean, approx_count_distinct ) bronze = spark.table("catalog.bronze.orders") silver = (bronze # standardise data types .withColumn("order_date", to_date(col("order_date_str"))) .withColumn("amount", col("amount").cast("double")) .withColumn("status", upper(trim(col("status")))) # clean nulls .fillna({"amount": 0.0, "country": "UNKNOWN"}) .dropna(subset=["order_id", "order_date"]) # deduplicate .dropDuplicates(["order_id"]) # filter invalid rows .filter(col("amount") > 0) ) (silver.write .mode("overwrite") .option("overwriteSchema", "true") .saveAsTable("catalog.silver.orders"))
# Aggregations (Gold layer) gold = (silver .groupBy("order_date", "country") .agg( sum("amount").alias("total_revenue"), count("order_id").alias("order_count"), count_distinct("customer_id").alias("unique_customers"), approx_count_distinct("customer_id").alias("approx_unique"), avg("amount").alias("avg_order_value"), mean("amount").alias("mean_value") ) ) # summary() equivalent in Spark silver.summary().show() # count/mean/std/min/max/pct silver.describe("amount").show()
Exam trap: count("col") counts non-null rows. count_distinct("col") counts unique values. approx_count_distinct is a fast probabilistic alternative — used when exact count isn't required. These three appear as distractors in the same question.

DataFrame operations — joins, columns, rows high frequency

Lakeflow Declarative Pipelines — transformation layer in Section 3

Lakeflow Declarative Pipelines (formerly Delta Live Tables) is the managed ETL framework for building Silver and Gold transformation layers. You declare tables in SQL or Python; Databricks manages execution order, retries, data quality, and lineage. It is classified under Data Transformation in the May 2026 exam guide.

-- SQL: streaming live table (bronze ingest) CREATE OR REFRESH STREAMING LIVE TABLE bronze_raw COMMENT "Raw events" AS SELECT _metadata.file_name AS source_file, current_timestamp() AS ingest_time, * FROM cloud_files('/landing/', 'json', map('cloudFiles.schemaLocation','/chk')); -- SQL: live table with expectations (silver) CREATE OR REFRESH LIVE TABLE silver_orders ( CONSTRAINT valid_amount EXPECT (amount > 0) ON VIOLATION DROP ROW, CONSTRAINT has_customer EXPECT (customer_id IS NOT NULL) ON VIOLATION FAIL UPDATE ) AS SELECT * FROM LIVE.bronze_raw WHERE amount > 0; -- SQL: materialized view (gold) CREATE OR REFRESH MATERIALIZED VIEW gold_revenue AS SELECT order_date, SUM(amount) AS total FROM LIVE.silver_orders GROUP BY order_date;

Delta Lake DDL / DML — essential syntax

-- Create CREATE OR REPLACE TABLE t ( id STRING, dt DATE, v DOUBLE ) USING DELTA CLUSTER BY (id); -- Liquid Clustering CREATE TABLE IF NOT EXISTS t (...); CREATE TABLE t2 AS SELECT * FROM t; -- CTAS -- DML INSERT INTO t VALUES ('a1','2024-01-01',100.0); INSERT OVERWRITE t SELECT * FROM staging; UPDATE t SET v = v*1.1 WHERE dt='2024-01-01'; DELETE FROM t WHERE dt < '2023-01-01'; -- MERGE (upsert + CDC) MERGE INTO silver.orders t USING bronze.raw s ON t.order_id = s.order_id WHEN MATCHED AND s.op='DELETE' THEN DELETE WHEN MATCHED THEN UPDATE SET * WHEN NOT MATCHED THEN INSERT *;
-- Time travel SELECT * FROM t VERSION AS OF 5; SELECT * FROM t@v5; SELECT * FROM t TIMESTAMP AS OF '2024-06-01'; RESTORE TABLE t TO VERSION AS OF 3; -- Maintenance OPTIMIZE t; OPTIMIZE t ZORDER BY (country, dt); ALTER TABLE t CLUSTER BY (country, dt); -- Liquid VACUUM t RETAIN 168 HOURS; -- Inspect DESCRIBE TABLE EXTENDED t; DESCRIBE DETAIL t; -- file stats, location, type DESCRIBE HISTORY t; -- all versions + operations
OPTIMIZE vs VACUUM: OPTIMIZE compacts files but keeps old versions — time travel still works. VACUUM permanently deletes old files past the retention period — time travel past that point becomes impossible. Default retention = 7 days (168 hours).

Lakeflow Jobs — task types and DAG high frequency

Lakeflow Jobs is the native orchestrator. Tasks are wired into a DAG via depends_on. The exam tests task configuration, dependency logic, retry behaviour, and trigger types.

Task typeUse when

DAG patterns: Linear = A→B→C. Fan-out = A→[B,C,D] parallel. Fan-in = [A,B]→C (both must succeed). Diamond = fan-out + fan-in combined. All wired with depends_on lists.
# Pass values between tasks # Upstream task: dbutils.jobs.taskValues.set(key="row_count", value=12345) # Downstream task: count = dbutils.jobs.taskValues.get( taskKey="ingest_bronze", key="row_count", default=0 ) # Conditional task (run_if) # ALL_SUCCESS (default) # AT_LEAST_ONE_SUCCESS # NONE_FAILED # AT_LEAST_ONE_FAILED ← run a cleanup on failure # ALL_DONE ← always run (e.g. notification) # Retry policy (per task) # max_retries: 3 # min_retry_interval_millis: 60000 (1 min) # retry_on_timeout: true # Repair & rerun (after failure) # Re-runs ONLY the failed task + downstream dependents # Successfully completed tasks are NOT re-run
Exam trap: "Repair run" re-executes from the failed task only — not the full job from the start. Choosing "re-run entire job" is always wrong for recovery/efficiency questions.

Trigger types and scheduling exam guide explicit

The exam asks you to choose the right trigger type based on how data arrives and pipeline dependencies. Three trigger types are explicitly named in the exam guide.

Trigger typeHow it firesChoose when
Scheduled (time-based)Cron expression — runs at fixed intervals (hourly, daily, etc.)Data arrives on a predictable schedule; SLAs measured by clock time

# Cron schedule example (Quartz format) # "0 0 6 * * ?" = 6:00 AM every day # "0 0/30 * * * ?" = every 30 minutes # "0 0 8 ? * MON-FRI" = 8 AM weekdays # File arrival trigger # Set in Lakeflow Jobs UI: # Trigger type: File arrival # Storage location: s3://bucket/landing/events/ # Table update trigger # Trigger type: Table update # Table: catalog.silver.orders # Control flow: branching example # Task A finishes → check row_count value count = dbutils.jobs.taskValues.get("taskA","row_count",0) if count == 0: dbutils.notebook.exit("skip") # signal to skip downstream # Looping: use a For Each task in Lakeflow Jobs UI # Iterates over a list of values, running a task for each

Control flow — retries, branching, looping

  • Retries — set max_retries per task; use retry_on_timeout=true for flaky network ops; configure backoff with min_retry_interval_millis
  • Conditional tasks — use run_if to run a task only when upstream succeeded / failed / always
  • Branching — notebook exits with a value; downstream tasks check taskValues to decide path
  • For each task — built-in Lakeflow Jobs UI feature; iterates a task over a list of inputs
  • Timeout — timeout_seconds per task or per job; auto-cancels overrunning runs
  • Max concurrent runs — prevents overlapping scheduled runs on the same job

Job monitoring with Lakeflow Jobs UI

  • Run history view — compare current execution times against historical baselines; spot duration trends
  • DAG-based task graph — visually see upstream blockers; identify which task caused a cascade failure
  • Job statuses — Pending / Running / Succeeded / Failed / Cancelled / Skipped
  • Pipeline run times and failure rates — track SLA compliance over time
  • Task-level logs — driver log, stderr, stdout accessible per task run
  • Notifications — email / webhook / PagerDuty on success or failure

Declarative Automation Bundles (DABs) renamed from Asset Bundles sample Q5

Declarative Automation Bundles (formerly Databricks Asset Bundles) package jobs, pipelines, notebooks, and configs as YAML code in Git. They enable repeatable CI/CD deployments across dev, test, and prod environments. Sample Q5 confirms DABs are the correct answer for "modular, versioned, Git-promoted ETL pipelines."

Liquid Clustering and Predictive Optimization exam guide explicit

Both are named explicitly in the exam guide for Section 6. Liquid Clustering replaces static partitioning and Z-ordering; Predictive Optimization automates maintenance operations.

  • Liquid Clustering — replaces static PARTITIONED BY and Z-ordering; dynamically re-clusters data based on actual query patterns; multi-column; incremental — doesn't require full rewrite
  • Enable on new table: CREATE TABLE t CLUSTER BY (col1, col2)
  • Enable on existing: ALTER TABLE t CLUSTER BY (col1, col2)
  • Still requires OPTIMIZE to actually trigger clustering of new data
  • Best for: high-cardinality columns; frequently changing filter columns; tables that evolve over time
-- Enable Liquid Clustering CREATE TABLE events ( id STRING, country STRING, event_date DATE ) CLUSTER BY (country, event_date); -- Change clustering columns ALTER TABLE events CLUSTER BY (user_id, event_date); -- Trigger clustering of new data OPTIMIZE events;
  • Predictive Optimization — Databricks automatically runs OPTIMIZE and VACUUM on Unity Catalog managed tables based on usage patterns; no manual scheduling needed
  • Enabled at the UC metastore or catalog level by an admin
  • Analyses table access patterns to determine when OPTIMIZE is beneficial
  • Prevents the small-file problem without manual maintenance jobs
  • Currently supported for UC managed tables only (not external tables)

Cluster startup failures, library conflicts, and OOM

The exam gives a symptom and asks for the diagnosis. Know the three main failure categories and their signatures.

Cluster startup failures
  • Symptoms: cluster stays in "Pending" or "Error" state; never reaches "Running"
  • Cloud quota exceeded — request more vCPUs in cloud console
  • Init script failure — check driver logs > init script output
  • Wrong instance type for region — change node type
  • Network/VNet misconfiguration — check security group / NSG rules
  • IAM / service principal lacks permissions to spin up VMs
Library conflicts
  • Symptoms: ImportError, ClassNotFoundException, version mismatch errors in task logs
  • Conflicting versions between cluster-installed and notebook-installed libraries
  • Fix: use %pip install in notebook (notebook-scoped; takes priority)
  • Pin library versions in cluster config or requirements.txt
  • Use cluster policies to enforce standard library sets
  • Check DBR version compatibility for each library
Out-of-memory (OOM)
  • Symptoms: java.lang.OutOfMemoryError; task killed; executor lost; spill to disk warnings in Spark UI
  • Executor OOM: increase spark.executor.memory; reduce shuffle.partitions; avoid collect() on large DFs
  • Driver OOM: increase spark.driver.memory; avoid .collect() / .toPandas() on large datasets
  • Spill to disk → memory pressure; increase executor memory or add nodes
  • GC > 5% in Spark UI Executors tab → memory pressure signal

Unity Catalog — hierarchy and permissions high frequency

Unity Catalog uses a three-level namespace — catalog.schema.table. Users need USE access at every level before object-level privileges apply. This hierarchical requirement is the most tested concept in Section 7.

-- Minimum read access (all three required!) GRANT USE CATALOG ON CATALOG prod TO analysts; GRANT USE SCHEMA ON SCHEMA prod.sales TO analysts; GRANT SELECT ON TABLE prod.sales.orders TO analysts; -- Schema-level (covers all current + future objects) GRANT SELECT ON SCHEMA prod.sales TO analysts; GRANT MODIFY ON TABLE prod.sales.orders TO `eng`; GRANT CREATE TABLE ON SCHEMA dev.staging TO `eng`; -- Catalog-level GRANT ALL PRIVILEGES ON CATALOG dev TO `dev-team`; GRANT CREATE SCHEMA ON CATALOG dev TO `eng`; -- DENY: explicitly blocks even if GRANT exists elsewhere DENY SELECT ON TABLE prod.sales.pii_data TO contractors; -- Revoke and inspect REVOKE SELECT ON TABLE t FROM analysts; SHOW GRANTS ON TABLE prod.sales.orders; SHOW GRANTS TO analysts;
